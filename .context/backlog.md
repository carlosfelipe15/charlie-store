*   [x] **[DATA/INDEX-STALE]** Filtrar productos por marca en el storefront devolvía "0 productos" para las marcas agregadas por `seed-mercado-catalog.ts`, y el admin no mostraba los productos nuevos apenas se aplicaba cualquier filtro (status, búsqueda).
    - *Resuelto el:* 2026-07-12 por Claude, a pedido de Carlos
    - *Causa raíz:* el Index Engine (`@medusajs/index`, ver "Índice de búsqueda cross-módulo" en `AGENTS.md`) mantiene sus tablas (`index_data`/`index_metadata`/...) sincronizadas vía eventos del event bus — en dev, el Local Event Bus ("not recommended for production"). Confirmado con SQL directo: `index_metadata.status = "done"` para las 9 entidades indexadas, pero `index_data` tenía solo 10 filas de `Product` y 4 de `Brand` contra 54 y 16 reales — todo lo creado desde el 2026-07-08 (incluyendo los 44 productos y 13 marcas de `seed-mercado-catalog.ts`, corrido vía `medusa exec`) nunca se indexó. `status: "done"` solo refleja que el *schema* indexado no cambió, no que las filas estén al día — falsa sensación de estar sincronizado. Causa de fondo: un script `medusa exec` es un proceso corto que termina apenas resuelve su función default, y los listeners que el Index Engine agenda de forma asíncrona en respuesta a los eventos de creación pueden no llegar a correr antes de que el proceso termine — a diferencia de un `medusa develop` de larga duración, donde sí corren.
    - *Fix:* nuevo script `apps/backend/src/scripts/reindex-search.ts` (correr con `pnpm medusa exec ./src/scripts/reindex-search.ts`) que trunca las 4 tablas del Index Engine y dispara `indexModuleService.sync({strategy: "full"})`. Nota de implementación no obvia: llamar `sync()` sin truncar antes **no alcanza** — el chequeo interno (`checkChanges()`) solo re-sincroniza una entidad si el *hash del schema* indexado cambió, no si las filas están desactualizadas, así que sin el truncate previo no hay manera de forzar un resync completo por API pública. Tampoco alcanza con correr el script `medusa exec` solo — en ese contexto el módulo corre en rol "server" (no "worker"), así que ni siquiera el resync se ejecuta de verdad ahí; hace falta que el proceso de `medusa develop` real (que sí corre en modo worker) arranque *después* del truncate para que su `onApplicationStart_` haga el backfill real. `seed-mercado-catalog.ts` ahora loguea un recordatorio de correr este script al final si creó productos/marcas nuevos.
    - *Verificado:* antes del fix, `GET /store/products-list?brand_id=<Chanel>` devolvía `count: 0`; después, `count: 1` con el producto correcto. `GET /admin/products` con filtro de status pasó de `count: 1` a `count: 29` (dato completo confirmado con `limit=100`, ver bug activo `[BUG/ADMIN-INDEX]` arriba sobre por qué el `count` en sí sigue sin ser exacto). `index_data` post-fix: `Product` 54/54, `Brand` 16/16 (match exacto con conteo real de las tablas `product`/`brand`).

## 🩹 Deuda Técnica y Refactorizaciones Minoritarias
*   [ ] **[DATA/REVIEWS]** No hay constraint ni validación que impida que un mismo customer deje varias reseñas sobre el mismo producto.
    - *Detectado el:* 2026-07-09 por Carlos
    - *Origen:* Ya documentado como pendiente en [docs/custom-features/reviews.md:100](docs/custom-features/reviews.md#L100) (tabla "Extender Reviews"), no es un hallazgo nuevo — se traslada aquí para que quede trackeado como ítem de backlog accionable en vez de solo mencionado en la doc de referencia.
    - *Impacto:* `createReviewStep` ([workflows/steps/create-review.ts](apps/backend/src/workflows/steps/create-review.ts)) inserta directamente sin verificar si ya existe una reseña de ese `customer_id` para ese `product_id`, y la migración de `review` ([modules/review/migrations/](apps/backend/src/modules/review/migrations/)) no tiene ningún índice único sobre `(product_id, customer_id)`. Un mismo cliente puede dejar N reseñas del mismo producto, infla el promedio/conteo que muestra `RodiProductReviews` y el endpoint `/store/reviews/summary`, y no hay forma de que la UI ofrezca "editar tu reseña" en vez de "crear otra" porque no hay unicidad que lo garantice.
    - *Posible solución:* Agregar un índice único compuesto `(product_id, customer_id)` en una nueva migración (no editar la migración inicial ya aplicada), y validar en `createReviewStep` (o antes, en la API route) si ya existe una reseña del customer para ese producto — devolver un error claro (ej. 409) en vez de dejar que la constraint de DB reviente como error 500 genérico. Nota: el plan pendiente de Favoritos (aún no implementado) ya contempla agregar este mismo tipo de constraint único desde el inicio en `favorite`, precisamente para no repetir este gap ahí también.

*   [ ] **[UX/FAVORITOS]** Los errores de "no logueado" en Favoritos no son descriptivos para el usuario final.
    - *Detectado el:* 2026-07-10 por Carlos
    - *Impacto:* Dos casos distintos, ambos con el mismo problema de fondo (mensaje genérico en vez de explicar que hace falta iniciar sesión):
      1. Al intentar marcar un producto como favorito estando deslogueado, se muestra "Unauthorized" en vez de un mensaje claro. `addFavorite`/`removeFavorite` ([lib/data/favorites.ts](apps/storefront/src/lib/data/favorites.ts)) ya tienen un guard explícito que debería devolver `"Inicia sesión para guardar tus favoritos."` cuando no hay `authorization` en los headers — a investigar por qué no está disparando en este caso (¿cookie de sesión inválida/expirada que sí matchea el guard pero el backend igual rechaza con 401 crudo, cuyo `error.message` se muestra tal cual en el `catch`?).
      2. Al navegar directo a `/account/favorites` deslogueado, se muestra la página 404 genérica de Next.js en vez de redirigir a login o explicar que la función requiere cuenta. (2) Para la página: es una decisión de UX más amplia para todo `account/@dashboard` (redirigir a `/account` con mensaje, en vez de `notFound()`) — si se aborda, conviene resolverlo para todas las páginas del dashboard a la vez, no solo favoritos, para no dejar el resto inconsistente.
